## API

Все методы требуют заголовки `Authorization: Bearer <токен>` и `Accept: application/json`. Без `Accept` запрос без токена вернёт 500 вместо 401.

| Метод | Адрес | Что делает |
| --- | --- | --- |
| GET | `/api/bookings` | Мои брони |
| POST | `/api/bookings` | Создать бронь |
| DELETE | `/api/bookings/{id}` | Отменить бронь |
| GET | `/api/rooms/{room}/bookings/today` | Брони комнаты на сегодня |

Пример:

```sh
curl -X POST http://localhost:8000/api/bookings \
  -H "Authorization: Bearer anna-token" \
  -H "Accept: application/json" \
  -H "Content-Type: application/json" \
  -d '{"room_id": 1, "user_id": 1, "title": "Планёрка", "starts_at": "2026-11-02T10:00:00+03:00", "ends_at": "2026-11-02T11:00:00+03:00"}'
```

Лог созданных броней пишется в `storage/logs/bookings.log`.

## Реализованное решение тестового задания

### Исправления API

Методы `store()` и `destroy()` в `app/Http/Controllers/BookingController.php` доработаны следующим образом:

- Входные данные проверяются до обращения к БД. Для `room_id` требуется существующая комната; время передаётся в ISO 8601 с явным смещением или `Z`. Ошибки валидации возвращаются с HTTP 422.
- Время начала и окончания интерпретируется как абсолютный момент времени, приводится к UTC и записывается в `timestamp without time zone` в едином соглашении (UTC). Правила рабочего дня проверяются в часовом поясе офиса комнаты (`Europe/Moscow` или `Asia/Novosibirsk`).
- Длительность должна быть от 15 до 240 минут включительно, с шагом 15 минут. Начало и окончание обязаны попадать на четверть часа местного времени офиса, а весь интервал — в пределах 09:00–20:00 одного местного дня.
- Пересечение определяется условием `existing.starts_at < new.ends_at AND existing.ends_at > new.starts_at`. Смежные интервалы не конфликтуют; пересечение возвращает HTTP 409.
- `user_id` берётся только из авторизованного пользователя. Отмена чужой брони запрещена (HTTP 403); успешное удаление возвращает HTTP 204.
- По условию задания `index()` и `today()` не менялись. Их проблемы описаны отдельно в `REVIEW.md`.

### Конкурентное создание бронирований (бонус)

Проверка пересечения и создание брони выполняются в транзакции. Перед запросом конфликтов выполняется `SELECT ... FOR UPDATE` по **строке комнаты** в таблице `rooms`. Таким образом, два вызова этого API для одной комнаты не смогут одновременно проверить пустой слот: второй дождётся завершения первого и затем увидит созданную бронь.

**Ограничение:** это защита на уровне приложения. Прямая запись в таблицу `bookings` другим кодом, который не блокирует строку комнаты, может обойти её. Полную гарантию на уровне PostgreSQL обеспечит `EXCLUDE USING gist (room_id WITH =, tsrange(starts_at, ends_at, '[)') WITH &&)` (после включения `btree_gist`) с преобразованием ошибки исключения PostgreSQL в HTTP 409. В этой реализации ограничение не добавлялось, а отдельный нагрузочный тест двух реальных параллельных запросов не проводился.
