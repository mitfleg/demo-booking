# Code review: `BookingController.php`

Анализ относится к **исходному** `app/Http/Controllers/BookingController.php`, до внесения исправлений. Номера строк указаны по исходной версии.

| Серьёзность | Место | Проблема и последствие | Исправление |
|---|---|---|---|
| **critical** | `store`, строки 21–24 | SQL-инъекция: `room_id`, `starts_at`, `ends_at` интерполируются в SQL. Пользователь управляет частью запроса; возможен обход проверки конфликтов и воздействие на БД. | Query Builder / Eloquent с параметризованными условиями и валидацией типов. |
| **critical** | `store`, строка 34 | `Booking::create($request->all())` позволяет подставить `user_id` другого пользователя (а также передать неподконтрольные поля). Это горизонтальное повышение привилегий. | Явно перечислять сохраняемые поля; `user_id` брать только из `$request->user()->id`. |
| **critical** | `destroy`, строки 42–45 | Удалить чужое бронирование может любой авторизованный пользователь, знающий его ID. | Найти бронь и проверить `user_id` текущего пользователя; для чужой записи вернуть 403 (или 404 по выбранной политике доступа). |
| **major** | `store`, строки 23–24 | Границы пересечений включительные (`<=` и `>=`), из-за чего встречи 10:00–11:00 и 11:00–12:00 ошибочно считаются пересекающимися. | Использовать полуоткрытые интервалы: `existing.starts_at < new.end && existing.ends_at > new.start`. |
| **major** | `store`, строки 21–34 | Проверка и вставка не атомарны. Два одновременных запроса могут увидеть свободный слот и создать две брони. | Транзакция с блокировкой строки комнаты (`SELECT ... FOR UPDATE`) и проверкой под блокировкой; альтернативно PostgreSQL `EXCLUDE`-constraint. |
| **major** | `store`, строки 29–32 | Проверяется только `starts_at`, и только в часовом поясе, который следует из входной строки. Часовой пояс комнаты вообще не учитывается. | Перевести оба момента времени в часовой пояс офиса комнаты перед проверкой рабочего интервала. |
| **major** | `store`, строки 29–32 | Не проверяется время окончания. Встреча может начаться в 19:00 и закончиться после 20:00 или на следующий день. | Проверять целиком интервал 09:00–20:00 в рамках одного локального дня офиса. |
| **major** | `store`, строки 19–34 | Нет ограничений на положительную длительность от 15 до 240 минут. Возможны нулевые, отрицательные и слишком длинные брони. | Вычислить длительность по абсолютным моментам времени в UTC и проверить диапазон. |
| **major** | `store`, строки 19–34 | Не проверяется шаг 15 минут, включая секунды и дробные секунды. | Проверять `:00`, `:15`, `:30`, `:45` по локальному времени офиса, секунды и микросекунды должны быть нулевыми. |
| **major** | `store`, строки 19–34 | Нет проверки обязательных параметров, существования комнаты и корректности ISO 8601. Это приводит к непонятным ошибкам и потенциальным 500. | Структурная валидация входа с понятными ответами 422. Требовать явное смещение времени или `Z`. |

В задании метод менять не требуется. |
| **minor** | `today`, строки 50–56 | Обращение `$b->user` после `get()` вызывает N+1 запрос для авторов, если связь не загружена. | `with('user')` перед выполнением запроса. В задании метод менять не требуется. |

## Подозрительные места, которые не являются ошибками

- `index`, строка 16: `orderByRaw('starts_at DESC')` **не создаёт SQL-инъекцию**, поскольку это константная строка без данных пользователя. `orderByDesc('starts_at')` читается проще, но метод менять по условиям не нужно.
- Маршруты API находятся внутри `auth:sanctum`: аутентификация присутствует. Проблема `destroy` состоит **в отсутствии авторизации на конкретную бронь**, а не в отсутствии защиты маршрута.
- Фиксированные демонстрационные токены подходят для локального тестового стенда, но не должны использоваться в рабочем окружении.

## Принятое решение

- Проверять и переводить входные даты в UTC; при проверке рабочих часов переходить в `office.timezone`.
- Сохранять UTC в существующие столбцы PostgreSQL `timestamp without time zone`, не смешивая локальные времена разных офисов.
- В критической секции блокировать строку `rooms`, затем проверять пересечение и создавать бронь. Это сериализует конкурентные создания броней одной комнаты **через этот код**; независимые записи в таблицу бронирований без использования блокировки смогут обойти эту защиту. Для гарантии на уровне БД полезен `EXCLUDE USING gist` на диапазонах времени.
- Для пересечения возвращать `409 Conflict`, для некорректных входных данных и бизнес-ограничений — `422 Unprocessable Content`, для попытки отмены чужой брони — `403 Forbidden`.

Исходный `index()` и `today()` оставлены без функциональных изменений согласно условию задания.
